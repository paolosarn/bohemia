## THE REAL VOCABULARY FOR "PLACE OR MENU": DIEGETIC VERSUS NON-DIEGETIC

This row's whole question already has a name in real game design: diegetic UI exists inside the
game's own world (a character could in principle see it); non-diegetic UI sits on top of the
screen as a pure overlay only the player sees. A row of labelled buttons captioned "BARBER,"
"MARKET," "BOARD" is non-diegetic -- exactly what Paolo called "options." A building drawn as a
building, in the scene, that you touch directly, is diegetic. Round two's "count the things that
read as buttons versus buildings" is, precisely, counting diegetic hits against non-diegetic
ones. The genre precedent for doing this well is older and more specific than 3D game UI: the
classic point-and-click adventure (Monkey Island, King's Quest) is built entirely from a painted
background with hidden interactive hotspots, named or highlighted only on touch or hover -- the
exact shape rule 71a already asked RUN TWO to build.
[Diegetic vs Non-Diegetic UI](https://punchev.com/blog/diegetic-vs-non-diegetic-game-ui)

## A REAL CAUTION FROM THE SAME GENRE, FOR ROUND TWO TO WATCH

The point-and-click genre's own hard-learned failure mode is "the pixel hunt": hotspots hidden so
well that players wander the screen hunting for them, which is why the genre converged on a
convention (a key that highlights every hotspot at once) rather than leaving discovery entirely
to chance. Rule 71a's own floor -- zero labels at rest, a building lights only under the finger --
is the correct diegetic choice and matches the genre's visual style, but round two should check
for the genre's usual MITIGATION too: is there any affordance (a subtle highlight, a cursor
change, anything) that tells a new player buildings ARE touchable, short of a permanent label? If
there is none at all, that is worth naming as a real risk, not assumed to be fine because the
floor says zero labels.
[Point-and-Click Game design](https://tvtropes.org/pmwiki/pmwiki.php/Main/PointAndClickGame)
