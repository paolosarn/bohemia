================================================================================
MEASURED BEFORE A LINE WAS WRITTEN
================================================================================
wasOf(person) is engine/bohemia_people.js's answer to "what did this person used
to be." It has one gate: `person.key`. No key, no answer. That gate exists for a
real, documented reason -- its own comment describes a 9/6 bug where the walked
city's roster object (carrying `id`) and the card's person object (carrying
`key`) answered DIFFERENTLY for the identical human, because hashing the bare id
and hashing the prefixed key are different hash inputs. The fix at the time was
to refuse without a key. Correct, but not the only correct answer, and it left a
new failure mode open.

UI's companion page reads bohemia_population.js's personFields() output straight
off the roster -- the RAW record the whole city is generated from, one layer
further back than the wrapped roster object the 9/6 bug came from. That record
carries `id` and never `key`. So the same defect class UI's own page just hit,
one hop earlier: ask the same real person two different ways and get two
different answers -- except this time one of the two answers was nothing.

================================================================================
WHAT WAS BUILT
================================================================================
wasOf() now derives a key from `person.id` when `person.key` is absent, but NOT
by hashing the bare id (the exact thing that caused the 9/6 bug). It builds the
SAME PREFIXED KEY the proper wrapper would have built: 'P:city:' + id, which is
the documented, already-used convention for turning a city population record
into a person everywhere else in this codebase (BOHEMIA_CITY_WORLD.html:
{ key: 'P:city:' + list[i].id, __p: list[i] }, repeated at four other call
sites). Hashing that prefixed key, not the bare id, is what keeps a raw record
and its properly wrapped twin answering identically -- the actual invariant the
9/6 fix existed to protect, now held one layer further back too.

A second id shape exists in this codebase: household agents, formatted
'H<house>-<n>', which need a blockSeed no lone object carries to build a correct
key (a DIFFERENT keyOf() function entirely, engine/bohemia_people.js:1823). Those
are matched by regex and still refused outright, not guessed at -- silence stays
the honest answer where the real answer is genuinely unknowable from the object
alone.

Applied to both copies (engine/bohemia_people.js and the inlined twin in
slices/BOHEMIA_CITY_WORLD.html), which were confirmed byte-identical in this
function both before and after, per ENGINE SYNC LAW.

================================================================================
PROVEN, NOT ASSERTED
================================================================================
Pulled 24 real people from the live population generator (six neighbourhoods,
four residents each), and for every one: called wasOf() on the raw record AND on
that same record properly wrapped with its real key, and compared the answers.
24 of 24 matched. Zero mismatches. That is the test that actually matters --
"one human, one past" was never about whether an answer exists, it is about
whether every object shape that can ask gives the SAME one.

Also proven: a household-agent-shaped id ('H3-2') is still refused (null), not
guessed at; an empty object and a null person are still refused, unchanged.
