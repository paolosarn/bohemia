# THE SUBURB NEVER HAD THE KIT -- a load-order landmine that took 32 gates red at once (8/3/26, RUN lane)

## WHAT HAPPENED

The D1 sidewalk fix made `engine/bohemia_suburb.js` call `K.layWalks(...)` -- the first
line in that module's history that ever actually reached for the district kit at
generate time. Every gate that walks the world went red in one suite run:

```

ZOOM SEAM, INTERIOR WALL, DOOR SWING, DOOR JAMB, RIG CHECK, PARTS PAINTED, BODY
VARIATION, LIFE, DRESS, POPULATION, MEMORY, DEVIATION, QUEST PLACEMENT, CURRENT
SLICE, INTEGRATION, THE RUN, RENDER PIXEL, CITY PEOPLE, MASS EDIT, ONE WORLD TAB,
NO PRISON, WALL CLASS, THREE-TILE WALL, FRONT DOOR, CANVAS SCALE, INTERIORS, MAP TAB
```

**And the alpha still booted with zero page errors.** Nothing looked wrong until you
walked into a suburb.

```
TypeError: Cannot read properties of undefined (reading 'layWalks')
    at layWalks   (about:srcdoc:3089)
    at denseFill  (about:srcdoc:3215)
    at generate   (about:srcdoc:3253)
    at __subBlock (about:srcdoc:9265)
    at __subGrid  (about:srcdoc:9271)
```

## ROOT CAUSE

The alpha's CITY app inlines ~40 engine modules into one script in a fixed order.
Measured, from the blob's own banners:

```
line 2950   /* ==== engine/bohemia_suburb.js ==== */
line 3335   /* ==== engine/bohemia_district_kit.js ==== */
line 3830   /* ==== engine/bohemia_apartment.js ==== */   ... and 37 more, all after
```

**The suburb is the ONE district of thirty-nine that loads BEFORE the kit.** Every
district module opens by CAPTURING the kit at load time:

```js
var K = (typeof module!=='undefined') ? require('./bohemia_district_kit.js')
      : (typeof BohemiaDistrictKit!=='undefined'?BohemiaDistrictKit:root.BohemiaDistrictKit);
```

For the suburb, at line 2950, `BohemiaDistrictKit` does not exist yet. `K` froze as
`undefined` and stayed that way for the life of the app. It was harmless only for as
long as nothing in the module ever asked the kit for anything.

## THE OTHER HALF, MEASURED IN THE RUNNING APP

```js
BohemiaDistrictKit.types().length   // 35
types().indexOf('suburb')           // -1
```

**`K.register('suburb', ...)` at the tail of that file has never run in the CITY app.**
Same cause. And the comment sitting directly above the binding, dated 7/26, says the
whole point of that binding was to make the suburb register:

> "this one referenced a bare `K` guarded by `typeof K!=='undefined'`, so in the browser
> the guard silently swallowed it and the module NEVER registered with the district kit."

The 7/26 fix corrected the *guard* and left the *load order*, so the symptom survived
the fix that was written for it. A comment claiming a bug is fixed is not a gate.

## THE FIX

Stop capturing. `K()` is an accessor that resolves at CALL time, by which point the
kit is always up, so load order cannot decide it any more.

Registration behaviour is **deliberately unchanged** -- the tail still asks at load
time, so it still no-ops in the CITY app exactly as it does today. Newly registering
Paolo's spawn district would change what the walked suburb is generated by, and that
is a measured change with its own before/after, not a side effect of a crash fix.
**[PENDING] the suburb's absence from the CITY registry is a real defect and it is
now written down instead of invisible.**

Re-proved after the fix: 36 suburb blocks, 589,824 cells, generated against `8e193ba`
and against the fixed module -- 0 differing blocks, identical md5
`5c584f8aa55016c8d32e1fbf51b41a91`.

## THE GATE

`gates/city_kit_binding_gate.js`, registered as KIT BINDING. Two halves:

1. **STATIC, on the shipped blob** -- read the module banners, find where the kit is
   inlined, and for every engine module inlined AHEAD of it that mentions the kit at
   all, fail if it captures the kit at load time. Lazy or after the kit; there is no
   third option that works.
2. **LIVE, in the browser** -- boot the run, enter the walked world, generate a spread
   of cells across the spawn district and render. **A blob that parses is not a blob
   that runs**, and that is precisely the gap that let this ship: `page.on('pageerror')`
   was silent the whole time because the throw happens inside the world's own
   try/catch path, on a tab you have to walk into.

```
CITY KIT BINDING GATE: 12 passed, 0 failed
```

## THE LESSON FOR THE NEXT SESSION

A green boot is not a green world. Any gate whose evidence is "the page loaded" is
measuring the wrong thing -- the same class of mistake as counting a `drawImage` call
that gets painted over (see `records/BOHEMIA_THE_SIDE_DOOR_HE_COULD_NOT_SEE_8_3_26.md`,
same day). Make the world GENERATE and RENDER in the gate, then look at what came out.
